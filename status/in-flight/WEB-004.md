## What is outstanding

## Check 1 — PASSED, 2026-09-09

Run at `/diagnostics/queue` on a loopback development server. The owner reports running the full sequence in **both Chrome and Safari**; the output below is the run pasted into the session, and **no `FAIL` line was observed in either browser**.

Buttons were pressed in the required order, with a page reload between the first and the third, because *Run native storage tests* leaves the recovery fixture that *Recover pending clips* then reads back from disk.

**What that last line settles.** `captureSession` committed a chunk **before** session stop, which is the collision-sensitive change WEB-004 made to `capture.ts`; the former design materialized chunks only at stop. A commit count of zero before stop would have failed the check.

**What it does not settle.** The budget test aborts a real transaction but does not exhaust a physical disk, and the synthetic capture uses an oscillator, not a microphone. Checks 2 and 3 below are where real audio and real storage pressure enter.

## Still outstanding

**Check 2 — the real recorder.** Record, disconnect the network, stop, then reload the same origin. Pending audio must recover, reconnect must process once locally, raw Blobs and results must be retained, and **playback must not reset every five seconds** — that was a real defect the independent checker found and fixed, and no browser has confirmed the fix. Repeat with two tabs and an interrupted response. Remote provider work may still repeat, because ADR-016's job ledger is in-process and best-effort.

**Check 3 — real storage pressure.** Exercise actual browser quota exhaustion or a private window, plus a mid-recording write failure. Capture must stop, previous commits must remain, unsaved audio must be downloadable, and no raw copy may be deleted automatically.

**Check 4 — deferred, not outstanding (ADR-013).** Physical mobile. Its precondition is now met, but it is a different task on a different device.

## How to run it

The development server needs, and none of this requires real credentials:

```
ECHO_OWNER_USERNAME=<anything>
ECHO_OWNER_PASSWORD=<32+ characters>
TRANSCRIPTION_PROVIDER=fixture
LLM_PROVIDER=fixture
```

Then open `/diagnostics/queue` as the owner. The page is development-only and owner-gated; it 404s on a production deployment, which the deployed check verifies.

## What changed underneath this

**Echo is now deployed over HTTPS and verified** (2026-09-08). That matters here: `checksum()` needs `crypto.subtle`, which browsers expose only in a secure context, so the durable queue can now be exercised somewhere other than the development machine. Acceptance can still be done locally on `127.0.0.1`, which is also a secure context — the deployed origin simply makes a second device possible.

## Not this task

Mobile capture acceptance is its own task and is not yet opened. It is unblocked (ADR-013's precondition is met) but it is a different set of checks on a different device.
