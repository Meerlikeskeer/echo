## Defects found while diagnosing, none of them covered by any test

Found on current `main` by reading the source, after a long and avoidable diagnosis. **None is WEB-004's fault and none should be fixed inside WEB-004.** They need their own task.

1. **`queue.error` is sticky and outlives the failure it describes.** `persist()` sets it when a chunk fails to save. Nothing clears it except a later successful `prepare()`, which only runs when the owner presses Record. A chunk that fails once and then saves on retry leaves the warning on screen indefinitely, next to a queue showing zero unsaved clips. Observed live: the owner saw "Local saving failed. Recording stopped." for an extended period while two clips sat saved and processed, and pressing Record started a recording immediately and cleared it.
2. **The generic storage message is actively misleading.** `storageFailure()` names only `StorageBlockedError` and `QuotaExceededError`; everything else collapses to "Local saving failed. Recording stopped. Keep this page open and download unsaved clips before leaving." That sentence asserts recording stopped when it may never have started, and directs the owner to rescue unsaved clips when there are none. It sent this session to clear site data, which destroys saved audio and is precisely what the retention rules forbid as a remedy.
3. **Nothing anywhere is logged.** There is not one `console` statement in the recorder, the queue hook or the queue module. The underlying error is caught, mapped to a sentence and discarded. Diagnosing item 1 took several rounds of hand-written console snippets reading IndexedDB directly, because the actual error was unrecoverable. This is the root cause of the other two being hard to see, and it is the one worth fixing first.

**Ruled out along the way, so nobody re-investigates.** Stored chunks verify correctly: metadata valid, blob sizes and MIME types matching, SHA-256 checksums matching. Safari reports ample quota, roughly 82 GB free against 338 KB used, so the capacity reserve is not firing. `DOMException` passes `instanceof Error` in Safari, so quota errors do map to the right message. The v1 to v2 migration was never exercised, because the browser never ran the new code.

**Environment traps that cost this session hours, all worth writing down.**

- The development server binds IPv4 only. Safari must be pointed at `http://127.0.0.1:3000`, never `localhost`, which Safari resolves to IPv6 first and then abandons. This is very likely what defeated the earlier attempt recorded as blocked in draft pull request #13, whose note reads "Safari could not connect to the development server".
- Updating the checkout does not update a running development server. Restart it, and confirm the page no longer reads "Overlapping speech is not stitched", a sentence that exists only in pre-WEB-006 code.
- Clearing site data appears to fix storage problems only because it destroys the evidence. It is never a diagnosis.

## How to run it

The development server needs, and none of this requires real credentials:

```
ECHO_OWNER_USERNAME=<anything>
ECHO_OWNER_PASSWORD=<32+ characters>
TRANSCRIPTION_PROVIDER=fixture
LLM_PROVIDER=fixture
```

Then open `/diagnostics/queue` as the owner. The page is development-only and owner-gated; it 404s on a production deployment, which the deployed check verifies. Parts B and C of the acceptance script call the real providers, so those need the `TRANSCRIPTION_*` and `LLM_*` groups.

## What changed underneath this

**Echo is now deployed over HTTPS and verified** (2026-09-08). That matters here: `checksum()` needs `crypto.subtle`, which browsers expose only in a secure context, so the durable queue can now be exercised somewhere other than the development machine. Acceptance can still be done locally on `127.0.0.1`, which is also a secure context — the deployed origin simply makes a second device possible.
