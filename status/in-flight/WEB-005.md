# WEB-005 — Incremental upload and transcription

**Branch:** `feat/WEB-005-incremental-upload` · **Base:** `main` @ `b44ec5b` (includes ENG-014)

## What I am attempting

Make Echo upload and transcribe **while recording continues** (REQ-003), with durable
per-chunk status, bounded retry, and jobs that are idempotent across a retry — so a
lost HTTP response does not make a provider process the same audio twice.

## Why this is not already done

WEB-004 built the durable queue but deliberately drained it **only after capture stopped**:
`useAudioQueue.sync()` returns early while `captureActive.current` is true. WEB-004's own
handoff records the remaining gap: *"exactly-once remote provider processing after a lost
HTTP response needs later server work — retries never duplicate a local chunk or result,
but a provider may see the same audio twice."* That server work is this task.

## Planned shape (subject to the checker)

1. **Client — drain during capture.** Lift the `captureActive` block; drain on each durable
   commit, still under the `echo-audio-queue-drain` Web Lock so two tabs cannot double-send.
2. **Client — no head-of-line blocking.** `drainQueue` currently `break`s on the first send
   failure, so one bad chunk stalls every later one. Continue past a failed entry; keep
   breaking on offline/unmounted.
3. **Client — bounded retry.** A maximum attempt count moves an entry to `blocked` with a
   reason instead of retrying forever. Owner force-retry (`sync(true)`) still overrides.
4. **Client — durable in-flight status.** An entry that was mid-upload when the page died
   must be recoverable as such, not silently indistinguishable from never-sent.
5. **Server — idempotent jobs.** `POST /api/recordings` gains a job ledger keyed by chunk
   identity (`sessionId`/`id`/`checksum`). A replayed key returns the stored result without
   calling a provider; a concurrent duplicate joins the in-flight job rather than starting a
   second one. Behind a port, in-memory adapter, best-effort — see the ADR below.

## Decision required before code (ADR-016)

Where the job ledger lives is a **stack decision**: ARCHITECTURE.md lists database, object
storage and background/worker infrastructure as intentionally undecided, so a durable ledger
cannot be chosen here. ADR-016 must record the in-memory, per-instance adapter behind a port,
and state plainly what it does **not** promise: it is not exactly-once across a cold start,
across Vercel Fluid instances, or across a redeploy.

## Not this task

measurement (WEB-008), server-side audio storage or retention deletion (WEB-010).
WEB-004's outstanding native browser acceptance is a separate file and a separate task.
