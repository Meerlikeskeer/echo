# WEB-005 — Incremental upload and transcription

**Branch:** `feat/WEB-005-incremental-upload` · **Base:** `main` @ `b44ec5b` (includes ENG-014)

## Why this file still exists

The code is implemented, verified by test and pushed. **WEB-005 is not Done**, for one reason:
the wiring that makes the queue drain *during* capture has **no automated test**. See below.
When that is accepted in a real browser, update `TASKS.md` and delete this file.

## What is finished

- **ADR-016** committed before any code: upload during capture, and a job ledger keyed by
  chunk identity. It states plainly that the ledger is **not exactly-once**.
- Client: drain during capture; a failed entry no longer blocks the ones behind it; retry
  bounded at 8 attempts then `blocked` with a readable reason; `uploading` persisted, and
  recovery on load returns a stale `uploading` row to `pending` without touching `processed`.
- Server: `JobLedger` port plus an in-process bounded, expiring adapter. A replayed or joined
  answer is marked in a `replayed` body field and an `x-echo-replayed` header.
- Recorder shows per-chunk progress while recording. Nothing is stitched — that is WEB-006.

## What is NOT verified — the reason this task is open

**Acceptance items A1–A3 have no automated test:** that `sync()` drains while capture is
active, that `persist()` triggers a drain, and that capture never waits on it. They live in
`useAudioQueue`, which needs a DOM, `navigator.locks` and IndexedDB. This repository has no
browser test runner, and adding one would mean a new dependency, which ADR-016's task
constraints forbid. An independent checker read and traced the wiring and found it correct —
but read is not run.

Also unexecuted by any automated test: the `navigator.locks` fail-closed branch, and
`IndexedDBQueue.recover()` / `.update()` themselves (only the pure functions they delegate to
are tested).
