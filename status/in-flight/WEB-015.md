# WEB-015 — The recorder discards every error and its warning outlives the failure

**Branch:** `feat/WEB-015-recorder-error-reporting` · **Base:** `main` @ `f68ccca`

Opened from the three defects recorded in `status/in-flight/WEB-004.md`, found while diagnosing WEB-004's browser acceptance. None of them is WEB-004's fault and none belongs inside it. All three are on `main` and none is covered by a test.

## The three defects, in the order they are being fixed

**1. Nothing is logged — fixed first, because it is why the other two were invisible.** There is not one `console` statement in `apps/web/src/app/recorder.tsx`, `apps/web/src/app/use-audio-queue.ts` or `apps/web/src/lib/recording/queue.ts`. Every failure is caught, mapped to a sentence and discarded. Diagnosing defect 2 cost an afternoon of hand-written IndexedDB console snippets because the real error existed nowhere.

**2. `queue.error` is sticky.** The only `setError(null)` in the hook is inside `prepare()`, which runs only when the owner presses Record. A chunk that fails once and saves on retry leaves the warning up indefinitely beside a queue showing zero unsaved clips.

**3. `storageFailure()` collapses every unrecognised error into one false sentence.** It names only `StorageBlockedError` and `QuotaExceededError`; everything else becomes "Local saving failed. Recording stopped. Keep this page open and download unsaved clips before leaving." That claims recording stopped when it may never have started, and directs the owner to rescue clips that do not exist. It sent a session to clear site data, which destroys saved audio and is what the retention rules forbid as a remedy.

## Why the message is wrong only at some call sites

`apps/web/src/lib/recording/capture.ts:88` calls `stop()` when the persist callback throws, so "Recording stopped" is **true** for a chunk failing mid-capture. It is false for the other two situations, which share the same sentence today:

- `prepare()` failing, which the recorder maps before the microphone is ever opened — recording did not start.
- The five-second maintenance poll and the drain, which run with no capture in progress and no unsaved clip.

The fix gives `storageFailure()` a situation rather than inventing more error classes, because the caller knows the situation and the error does not.

## Not in scope

The stitching, migration and upload paths are untouched. This changes no persistence behaviour and deletes nothing: it changes what is reported and when a warning is withdrawn.
