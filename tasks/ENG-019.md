## ENG-019 — Stop the process from generating merge conflicts and locking agents out

**Status:** Implemented and verified; awaiting owner review · **Branch:** `eng/ENG-019-conflict-free-task-records` · **Dependencies:** ENG-014, ENG-018

**Acceptance:** No file that every task must edit. A tracked path matching `.env*` no longer exists, so a sandboxed agent can check the repository out. Test counts are measured, never typed.

### Why this exists

Four branches in one afternoon — WEB-015, WEB-007, ENG-016, ENG-018 — all conflicted on the same two files, `TASKS.md` and `STATUS.md`. Every conflict was additive: the correct resolution was always *keep both*. Separately, Codex could not create a worktree at all, and three sessions were spent diagnosing a dependency tree that had been destroyed by two agents sharing one checkout.

None of that was a hard problem. All of it was the process fighting itself.

### The three root causes, and the fix for each

**1. Files every task must edit.** `TASKS.md` held ~1,100 lines of task records and every task appended to the same region. `STATUS.md` carried the generated table and the verification counts. Any two open branches collided.

ADR-015 and ENG-014 had already found half of this — they split `STATUS.md`'s *In flight* section into one file per task for exactly this reason — and stopped there. This finishes it, and states the rule so it is not learned a third time: **no file that every task must edit.**

- Each record moved to `tasks/<TASK-ID>.md`. 35 files, split mechanically so the move is reviewable rather than a hand edit.
- `tasks/INDEX.md` is generated by `npm run tasks:build` and marked **`merge=union`** in `.gitattributes`, so two branches adding two rows merge themselves. A union merge can leave rows misordered, which `npm run tasks:check` catches and `tasks:build` fixes — a command instead of a hand-resolved conflict.
- `TASKS.md` became a short pointer document with stable prose. `STATUS.md` no longer contains the table.
- `scripts/status-table.mjs` is replaced by `scripts/tasks.mjs`; `npm run check` now runs `tasks:check`.

**2. A test count no task could compute.** The floor was a sentence in `STATUS.md`. WEB-015 and WEB-007 both branched from 114 unit tests and recorded 126 and 149; neither could see the other, both were right on their own branch, and both were stale on `main`, where the real number is **161**. A number every task must edit is a merge conflict with extra steps, and a number no task can compute correctly is worse than no number.

`npm run floor` now runs the three suites, counts what actually passed, writes `verification-floor.json`, and **refuses a count that went down**. It reads the pass and fail lines from the TAP summary, so a suite that failed or produced no summary records nothing. It is deliberately outside `npm run check`, which would otherwise run every suite twice.

**3. A tracked `.env.example` locked sandboxed agents out of the repository.** Agent sandboxes deny writes to every path matching `.env*` — correctly, since that is where secrets live. But the template was tracked, so `git worktree add` failed on `error: unable to create file .env.example: Operation not permitted` before a single test could run. The same rule blocked `git mv`, so it could not be renamed from inside a session either; it was untracked with `git rm --cached` and re-added as `env.example`. The `.gitignore` exceptions are gone: **a `.env*` path in this repository is a secret, without exception.**

### Also delivered

`HUMAN_TESTING.md`, at the owner's request: every check no agent can run, in one place, with steps written out and a results table each. Four sessions — browser acceptance, the deployed origin, mobile capture, and the GitHub settings only an owner can apply. It names Session A as the bottleneck for five implemented-but-not-Done tasks, and names auto-merge as the reason finished work sits unmerged.

### Two negative controls

| Broken condition | Result |
| --- | --- |
| `verification-floor.json` set above the real counts | `npm run floor:check` exits 1 and names each suite that fell, rather than silently recording the lower number. |
| A task file whose heading disagrees with its filename | `npm run tasks:build` exits 2 and names the file. A record that cannot be addressed by its id is how an index silently loses a task. |
