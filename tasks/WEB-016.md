## WEB-016 — Lecture-length sessions

**Status:** Implemented and verified by test; browser acceptance on a real long recording outstanding · **Branch:** `feat/WEB-016-long-sessions` · **Dependencies:** WEB-003, WEB-004, WEB-005, WEB-006

**Acceptance:** Record for the length of a lecture without an auto-stop, with every chunk accepted by the upload boundary, the local budget sufficient for the whole session, and the stitched transcript still reaching `final` when capture completes.

### Why this was a task rather than a constant

Three limits enforced the one-minute recording, in three files, and only one of them was the timer everybody noticed. `validateCaptureOptions` refused a chunk longer than 60 seconds, so raising the timer alone would have thrown before the microphone opened. `isAudioChunk` refused metadata spanning more than 120 seconds, and that function is also what `POST /api/recordings` validates uploads with, so a longer chunk would have been rejected as malformed at the boundary rather than merely refused at capture. Both ceilings moved to a single `MAX_CHUNK_MS`.

### The failure that shaped the design

A browser is free to ignore `audioBitsPerSecond`. Safari 26.4 was measured at 204 kbps (WEB-003 evidence), which makes a five-minute chunk 7.6 MB against a 4 MB clip limit. Nothing in the old code would have caught that: capture would have succeeded, the first chunk would have closed five minutes in, and every upload would have been refused permanently — for every chunk, for the whole lecture, with the audio stranded in the browser.

So the bitrate is requested *and* read back. `measureBitrate` constructs a recorder that is never started and returns what it reports; `safeChunkMs` shortens the chunk to fit the upload limit at that rate, with a 20% container margin and a 15-second floor. A browser that will not report a rate keeps the full five minutes, because guessing shorter on no evidence penalises every browser that behaves. `sendChunk` additionally refuses an oversized chunk locally, so the worst case is a named refusal rather than eight round trips per chunk.

### Verification

- `npm run check` exit 0 in a clean clone: `check:tracked`, `tasks:check`, lint, typecheck, 178 unit tests, production build, 11 production HTTP tests, 4 self-host parity tests. Run on Node 22.23.2, npm 10.9.8.
- New behavioural tests: the lecture-length option is accepted and the ceiling still refuses what is past it; five-minute chunk metadata survives the upload boundary's validator; the bitrate clamp keeps a 204 kbps browser under the clip limit, leaves an honest browser alone, treats an unreported rate as no evidence, and never clamps into uselessness; an oversized chunk is refused locally, permanently, with its own message, and a chunk exactly at the limit still sends.
- The session shell test now asserts the old one-minute promise is absent as well as asserting the new copy, so it cannot quietly return.

### Not verified

Everything that needs a real browser and a real microphone. Specifically: that Safari and Chrome honour the 32 kbps request in practice; that `measureBitrate` reports a usable number on Safari rather than 0; that the wake lock holds across a real lecture with notifications and app switches; that IndexedDB sustains a multi-hundred-megabyte session; and that a stitched transcript from eighteen chunks still reaches `final`. No long recording has been made on any browser. The four-hour runaway bound has never fired.
